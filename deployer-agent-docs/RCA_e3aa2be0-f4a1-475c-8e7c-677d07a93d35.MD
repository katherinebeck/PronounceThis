# RCA — pronouncethis.us (accent-coach-pro) `/api/health` reporting `database:false`

**Run:** e3aa2be0-f4a1-475c-8e7c-677d07a93d35 (redeploy, success, promoted; tier_1, cluster target-3)
**Live URL:** https://accent-coach-pro.emergent.host
**Mode:** read-only diagnosis. No pipeline run, no manifest edits.

## Reported symptom
New `GET /api/health` consistently returned `{"ok":false,"checks":{"auth_keys":true,"database":false}}` with ~3.2 s latency on 6 consecutive calls over ~15 s right after the deploy. Admin also reported being signed out of /admin right after the deploy. Preview returns `database:true` instantly.

## Verdict
**Production DB access is NOT degraded.** Only the `db.command("ping")` in the health route transiently exceeded its tight 3 s timeout, in a short burst, while all normal queries worked throughout and the ping succeeds again now. The admin sign-out is explained by pod replacement at deploy (session reset), not by DB loss.

## Evidence
1. **Ping failure is a TIMEOUT, not auth/permission.** The 6 warnings read `health: database ping failed:` with an **empty exception string** — the signature of `asyncio.TimeoutError` (no message). There is NO `not authorized ... to execute command { ping }` text anywhere. The role permits `ping`.
   - Timestamps: 01:03:02, 01:03:13, 01:03:19, 01:03:24, 01:03:29, 01:03:35 — a single ~33 s burst, now ended.
2. **Ping succeeds now.** Live `GET /api/health` returns HTTP 200, body `{"ok":true,"checks":{"auth_keys":true,"database":true},...}` in **803 ms**. So `db.command("ping")` against prod Mongo currently works and is fast.
3. **Normal DB access was never degraded.** Direct `find_one` on `users` succeeded against db `accent-coach-pro-test_database` (real production data). In the same window, `/api/auth/me`, `/api/admin/ingest/status`, `/api/admin/paid-count`, `/api/admin/users`, `/api/admin/payment-health`, `/api/admin/whoami`, `/api/scenes`, `/api/scenes/<id>` **all returned 200**. No 500s.
4. **No other Mongo errors.** No `ServerSelectionTimeoutError`, `NetworkTimeout`, `OperationFailure`, or `AutoReconnect` in the last 30–60 min. The only DB-related warnings are the 6 ping timeouts.
5. **MONGO_URL target.** Resolved server-side to `accent-coach-pro-test_database` with real users present → points at the expected production DB. YES.
6. **Pod health.** Pod `r-e3aa2be0...-ps62r` Running since 2026-10-22T20:34:30Z, `ready:true`, **restart_count 0**, no OOMKilled, no eviction, no CPU/memory pressure events.

## Root cause
The health route's `await asyncio.wait_for(db.command("ping"), timeout=3)` is too aggressive. A `ping` that has to wait on a cold/first server-selection to Atlas (SRV + TLS handshake + topology discovery) — or that is briefly starved because the event loop was busy servicing the admin page's burst of concurrent `/api/admin/*` calls — can exceed 3 s and raise `asyncio.TimeoutError`, which the route reports as `database:false`. This is a false-negative health reading, not loss of DB connectivity. Normal queries (which don't impose a 3 s ceiling) succeeded the entire time.

Secondary code smell: the handler logs the exception via `str(e)`, which is empty for `TimeoutError`, so the warning carries no diagnostic text.

## Admin sign-out
Not DB-related. A redeploy replaces the pod set entirely; any in-memory/session state is reset at the traffic flip, signing active admins out once. After the deploy the admin's `/api/auth/me` (×many) and `/api/admin/whoami` all return 200 — she is authenticated and using admin pages successfully. No auth 500s, no DB auth errors.

## Suggested fixes
- **Code (E1):** In the `/api/health` route, raise the ping timeout (e.g. 8–10 s) and/or warm the Motor connection at startup (an await ping in the startup hook) so the first/cold ping doesn't trip a 3 s ceiling. Log `repr(e)` / `type(e).__name__` instead of `str(e)` so future ping failures are diagnosable. Optionally treat a ping timeout as "degraded" rather than hard `database:false` to avoid false negatives. No redeploy of infra needed beyond shipping this code change.
- **User (test_and_verify):** The admin sign-out is expected on a redeploy (pod/session reset). Sign back in and confirm /admin works — it already does per the 200s observed. Re-poll `/api/health`; it returns `database:true` now.

## Not applicable
Not a secrets issue (MONGO_URL correct, role permits ping). Not a tier issue (no OOM/CPU pressure). Not a manifest/pipeline issue (deploy succeeded and promoted). Not reproducible in an eph sandbox (requires the live Atlas connection and concurrent load), so the timeout cause is inferred from the empty-string exception + live success, not sandbox-reproduced.
