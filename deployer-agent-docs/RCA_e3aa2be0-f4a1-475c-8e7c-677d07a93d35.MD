# RCA — pronouncethis.us DB stalls / "database:false" / slow DB endpoints

Deployment: accent-coach-pro (4b70c844…) · Active run: e3aa2be0 (redeploy, live 2026-10-22 20:35:57Z) · Tier: tier_1 "Launch" (CPU 250m req / **500m limit**, mem 1Gi/2Gi, replicas 2, VPA on) · Frontend: Cloudflare · DB: accent-coach-pro-test_database.

## Verdict
The previous "DB not degraded" conclusion was correct about the **Atlas cluster** but missed the real fault: an **intermittent in-process Motor stall driven by CPU / thread-pool starvation inside the backend container**. The cluster is healthy; the backend process cannot get CPU time to complete its Mongo socket I/O under load, so pings time out and `find_one` takes 50–125 s, while the pure-async event loop keeps answering non-DB routes fast. It escalates to periodic process restarts.

## Root cause (in-process CPU / thread-pool starvation)
- The backend uses one global `AsyncIOMotorClient` (server.py:87, no pool tuning) with **motor==3.3.1 / pymongo==4.5.0**. Motor 3.x is NOT natively async for the wire protocol — it **offloads blocking PyMongo socket I/O to a ThreadPoolExecutor**, sized from `os.cpu_count()` → ~min(32, 16+4)=**~20 threads**.
- The app additionally makes heavy use of `asyncio.to_thread(...)` for blocking external calls — ElevenLabs speech-to-speech (~1.2 s each), Stripe, Resend email, YouTube transcript fetch, revoicing (server.py 1333/1356/1509/1831/2038; dictionary.py; stripe_payments.py; caption_search.py; etc.). `to_thread` uses the default loop executor, also ~20 threads.
- The container is capped at **500m CPU (½ core)**. When a load burst hits — the **admin dashboard fans out ~10 DB-backed endpoints at once** (`/api/admin/ingest/status` polled ×23/×16/×10, plus buyers, line-checks, credits, users, paid-count, payment-health, whoami — all 200 but slow → "admin page takes a while to load"), plus caption-search and the per-restart ElevenLabs revoicing — up to ~40 threads contend for ½ core under the GIL. Motor's DB-I/O threads get starved of CPU, so `db.command("ping")` can't finish in 3 s and `find_one` queues for 50–125 s, while the asyncio loop still returns simple JSON between GIL hand-offs → non-DB endpoints stay at 0.2–0.5 s.
- This starvation escalates: the process stops servicing and is restarted (nginx connection-refused + fresh uvicorn at 01:12:55). VPA (vpa_enabled=true) can also evict/recreate pods to re-apply recommendations, adding disruptive restarts (second startup block at 21:58-21:59).

**Proven:** trivial query + slow app path + fast fresh client + responsive loop + a real process restart. **Inferred (no live-metric tool):** that the binding constraint is the 500m CPU limit × thread oversubscription; I could not read live CPU/throttle counters or Atlas internals.

## Suggested fixes
### Code (E1) — primary, no live-DB needed, fixes the oversubscription
1. **Bound the thread pools to the CPU allocation.** At startup set a small default executor, e.g. `loop.set_default_executor(ThreadPoolExecutor(max_workers=8))`, and cap Motor with `AsyncIOMotorClient(mongo_url, maxPoolSize=20, minPoolSize=1, waitQueueTimeoutMS=...)` so DB I/O threads aren't drowned by `to_thread` blocking calls. Sizing should track the container's real CPU limit, not `os.cpu_count()`=16.
2. **Make the per-restart startup work idempotent / cheaper.** The migrate + ElevenLabs revoice of 7 toponyms and the supabase admin-create over 52 users run on *every* process start; guard them so a restart doesn't re-run external calls (they log "migrated"/"re-voiced" each boot).
3. **Reduce admin fan-out.** The admin page triggers ~10 simultaneous DB endpoints; consolidate/cache (e.g. a single aggregated admin summary) to avoid the burst that tips the pool over.
4. **Fix the liveness/readiness probe path** (`/health` → `/api/health`) so probes test the real endpoint.
*(Not reproduced under load in the sandbox — it requires concurrent traffic + live secrets; diagnosed from logs + source + live latency probes.)*

### User — Resources (tier)
Raise CPU above tier_1's 500m limit (tier_2 "Grow" or higher) in Deployment Panel → Resources. This is **inferred, not a measured throttle** (no live CPU metric available to me), but the ½-core limit against ~40 oversubscribed threads is the structural cause of the starvation; more CPU directly relieves it. Best paired with the Code fix above — upgrading alone will raise the ceiling the app hits but not the oversubscription.

### Not the cause
Atlas cluster / data / indexes are healthy (fresh client fast, tiny data, correct index). No secret issue implicated.
