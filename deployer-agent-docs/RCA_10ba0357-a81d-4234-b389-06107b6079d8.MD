# RCA — Production login hang on authenticated requests (pronouncethis.us / accent-coach-pro)

## Problem statement
Backend requests carrying a Supabase ES256 Bearer token hang ~13–30s and then time out
(`curl -m 30` → `000`), e.g. `GET /api/auth/me`, `GET /api/pronounce?word=party`.
Unauthenticated `GET /api/auth/me` and `/api/health` return in ~0.3s. Same token hits the
preview backend in ~0.6s. Active run: `10ba0357-a81d-4234-b389-06107b6079d8` (redeploy,
frontend_type=cloudflare, tier_1).

## What the reporter hypothesized vs. what the evidence shows
The reporter suspected (a) the prod pod cannot reach supabase.co (egress/DNS/firewall),
(b) a differing SUPABASE_URL/JWKS env in prod, or (c) pod OOM/restarts. **All three are
disproven.** The cause is in the app's own code (two defects, both on the authenticated path).

### DISPROVEN — pod cannot reach supabase.co
Backend logs (active run, 19:41) show the prod pod reaching the **same supabase host and
sub-second**:
```
httpx - INFO - HTTP Request: POST https://alsbjfsoqtyiglqtlhdg.supabase.co/auth/v1/admin/users "HTTP/1.1 422 Unprocessable Entity"
supabase_auth - INFO - supabase admin create annayen@icloud.com → 422 {... email_exists ...}
```
Four such calls at 19:41:17–19:41:19, ~0.5s each. The JWKS endpoint
(`/auth/v1/.well-known/jwks.json`) is the same host. Egress/DNS/firewall to supabase.co is
healthy and fast.

### DISPROVEN — SUPABASE_URL / JWKS env differs in prod
`list_secrets` (active run) with expected-value comparison:
- `SUPABASE_URL` → `matches_expected = true` (`https://alsbjfsoqtyiglqtlhdg.supabase.co`)
- `REACT_APP_SUPABASE_URL` → `matches_expected = true`
- `SUPABASE_JWT_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ANON_KEY` → all present, non-empty.
Code derives `ISSUER = f"{SUPABASE_URL}/auth/v1"` and the JWKS URL from it, so the issuer the
decoder validates matches the token's issuer host. No auth-related env is missing or wrong.
(Note: `list_secrets` reads only the active run; I could not diff raw values against the previous
good run, but every auth key is present and the URL matches the token issuer — no regression signal.)

### DISPROVEN — OOM / restarts since deploy
`get_pod_events` (active run): no `OOMKilled`, no exit-137, `restart_count = 0` on running pods.
Prior pod terminations are `Completed (exit 0)` (normal rollout/scale-down). The only Warning is a
startup-probe `503` on the newest pod during boot (nginx `connect() refused to 127.0.0.1:8001`
before uvicorn bound) — benign boot-ordering noise, not a crash. tier_1 = 1Gi/2Gi mem,
250m/500m cpu; nothing indicates a memory ceiling hit.

### Token verification actually SUCCEEDS
The observed traceback reaches `supabase_auth.resolve_user_email` (called only AFTER
`verify_access_token` returns claims). So JWKS signature verification is working for the cached
path — the tokens are valid and being verified.

## Root cause #1 (PRIMARY — the hang): blocking JWKS fetch on the asyncio event loop
`backend/supabase_auth.py`:
```python
_jwks = PyJWKClient(f"{ISSUER}/.well-known/jwks.json", cache_keys=True) if SUPABASE_URL else None

def verify_access_token(token: str) -> Optional[dict]:      # <-- SYNC def
    ...
    key = _jwks.get_signing_key_from_jwt(token).key          # <-- blocking urllib on the loop
```
`backend/auth.py` `caller_email` (async) calls it inline:
```python
claims = supabase_auth.verify_access_token(auth[7:].strip())  # not awaited, no to_thread/executor
```
- `verify_access_token` is a **synchronous** function invoked directly inside an async request
  handler — it is NOT wrapped in `asyncio.to_thread` / `run_in_executor`. Verified by source:
  line 29 `def verify_access_token` (sync); `grep` shows no `to_thread`/`run_in_executor`.
- `PyJWKClient.get_signing_key_from_jwt` performs a **synchronous `urllib` GET** of the JWKS.
  PyJWT (pinned `PyJWT==2.12.1`) defaults the client timeout to **30s** and no timeout override is
  passed.
- With `cache_keys=True` the key is cached after first fetch, BUT on a **cache-miss** (a token
  whose `kid` is not in the cached JWKS — i.e. after Supabase rotates its ES256 signing keys)
  `get_signing_key_from_jwt` triggers a fresh blocking JWKS refetch.
- Because that network call runs **on the single uvicorn event loop**, any slow/stalled JWKS
  refetch freezes the ENTIRE worker — every in-flight request stalls until it returns or hits the
  30s urllib timeout. This exactly matches the 13–30s hang → `curl -m 30` → `000`, and matches
  why unauthenticated requests stay fast: no `Bearer` header ⇒ `caller_email` takes the cookie
  branch and never touches `_jwks`.

This is the differential: the ONLY blocking operation unique to the authenticated path is the
sync JWKS fetch. I did not reproduce a live stall (eph sandbox has no prod creds and the stall is
intermittent, tied to key-rotation cache-misses / transient supabase latency), so the stall itself
is strong circumstantial evidence + source analysis, not a captured repro.

## Root cause #2 (SECONDARY — intermittent 500 on first login): DuplicateKeyError race
`fetch_app_logs` (active run) shows an unhandled ASGI exception on `GET /api/auth/me`:
```
File "/app/backend/auth.py", line 510, in me
File "/app/backend/auth.py", line 209, in caller_email
File "/app/backend/supabase_auth.py", line 68, in resolve_user_email
pymongo.errors.DuplicateKeyError: E11000 duplicate key error collection:
  accent-coach-pro-test_database.users index: email_1 dup key: { email: "ptbuyer114077@gmail.com" }
```
`resolve_user_email` does find-by-`supabase_sub` → None → find-by-`email` → None → `insert_one`.
On first login a SPA fires several authenticated requests concurrently (e.g. `/auth/me` +
`/pronounce`) with the same token; two coroutines both pass the find-by-email check and both
`insert_one`, so the loser raises `DuplicateKeyError` (unique index `email_1`) → unhandled → 500.
This is a fast 500, distinct from the hang, but it is a second real defect on the same path.

## Suggested fixes (NOT applied — diagnosis only, as requested)
Both are code fixes for E1 (the main agent); neither is a secret, infra, tier or DB-data issue.

1. **(Primary) Stop blocking the event loop on JWKS.** Make token verification non-blocking:
   either `await asyncio.to_thread(supabase_auth.verify_access_token, token)` in `caller_email`,
   or switch to an async JWKS client. Also pass an explicit short timeout to `PyJWKClient`
   (e.g. `timeout=5`) and add `lifespan_cache_keys` / periodic refresh so a rotated-`kid`
   cache-miss cannot freeze the worker for 30s. Prewarming the JWKS at startup also helps.
2. **(Secondary) Make first-login user creation race-safe.** Replace the find-then-`insert_one`
   in `resolve_user_email` with an idempotent upsert (`update_one(..., upsert=True)` on the unique
   key), or catch `DuplicateKeyError` and re-read the existing row, so concurrent first-login
   requests cannot 500.

## Not the cause (explicitly cleared)
- Supabase egress/DNS/firewall from the pod (reachable, fast).
- `SUPABASE_URL`/JWKS/auth env values (all correct, present).
- Pod OOM/memory/tier (no OOMKilled, restart_count 0).
- Preview `.env` carry-over (`AZURE_SPEECH_KEY/REGION`, `PRACTICE_MODE=on`) — benign, unrelated
  to auth; no auth-related env changed in a way that breaks verification.

Do not redeploy to "fix" this — the image change must come from E1 editing
`backend/supabase_auth.py` / `backend/auth.py`.
