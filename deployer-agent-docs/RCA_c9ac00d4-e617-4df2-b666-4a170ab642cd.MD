# RCA — build fails on `torch==2.14.1+cpu` (run c9ac00d4-e617-4df2-b666-4a170ab642cd)

## Symptom
`build_image` fails at the backend pip install step:
`ERROR: No matching distribution found for torch==2.14.1+cpu` — reported from `backend/requirements.txt` line 142.

## The key fact about how the deploy pulls source
The deploy pipeline does **NOT** do a `git checkout`. The `pull_source` step copies the **preview pod's working `/app` directory** (excluding `.git` and `node_modules`), zips it, and the build installs from that zip. So git HEAD / commit SHAs are irrelevant to what gets built — the build only ever sees the preview pod's live filesystem.

## Evidence (from the exact source this run built — eph sandbox of run c9ac00d4, source at /app/scratch)
- `wc -l backend/requirements.txt` → **160 lines** (your git HEAD 16a3eda has 147).
- Offending lines present in the pulled file:
  - `135: soundfile==0.14.0`
  - `141: tokenizers==0.23.3`
  - `142: torch==2.14.1+cpu`  ← exact line + content the build reported
  - `144: transformers==5.20.0`
  These are precisely the lines you said commit 70e434d removed. They are still present in the file the build used.
- **No `.git`** in the pulled source (`no .git in pulled source`) — confirms the build is the preview-pod filesystem copy, not a git revision.
- `Dockerfile.cloudbuild` installs the file verbatim: `pip install --no-cache-dir --no-dependencies -r /app/backend/requirements.txt` (lines 238–250). The only mutations are `sed` deletes of `litellm`/`emergentintegrations`. **No `pip freeze`, no requirements regeneration.**
- `.emergent/` contains only `emergent.yml`, `system_deps.txt`, `crons.yml`, `cron/`, `markers/` — **no requirements file or lockfile**. Only other lock files found are `frontend/yarn.lock` and root `yarn.lock`. No `.emergent` manifest carries the torch pin.

## Answering the three hypotheses
- **(a) Building from an older commit/checkpoint?** No. There is no SHA involved — the pipeline never uses git; it zips the preview pod `/app`. There is no `.git` in the build input.
- **(b) Regenerating via `pip freeze` from the preview venv?** No. The Dockerfile installs `requirements.txt` as-is; nothing freezes or rewrites it. The torch line is physically in the committed-to-pod file, not injected at build.
- **(c) Cached manifest/lockfile (`.emergent/`, build cache) carrying the pin?** No. `.emergent/` has no requirements/lock content; no alternate requirements file exists.

## Actual source of the pin
The **preview pod's working-tree file `/app/backend/requirements.txt`** still contains the torch/transformers/soundfile/tokenizers block. Your git HEAD (16a3eda) removed them in 70e434d, but the preview pod filesystem — the thing the deploy actually pulls — was never synced to that state. Your git clone's working copy matching HEAD is a different filesystem from the preview pod.

(Secondary: even if the base image had torch, `torch==2.14.1+cpu` is a `+cpu` local-version wheel that lives only on the PyTorch CPU index; there is no `--extra-index-url` in the file, so the pin is unsatisfiable regardless. The fix is to remove the line, not add the index.)

## Fix (no deploy performed — diagnosis only)
1. Edit the file **in the preview environment** (the `/app/backend/requirements.txt` that the deploy pulls), removing lines 135/141/142/144 (and any related `--extra-index-url`/`--index-url` ML lines). Make the preview pod file match your intended HEAD.
2. Do **not** rely on your local git clone or a commit SHA — confirm the change is present in the preview pod's `/app/backend/requirements.txt` before redeploying. A simple check after editing: the file should be 147 lines with no `torch`/`transformers`/`soundfile`/`tokenizers` entries.
3. Redeploy. There is no server-side build cache or `.emergent` manifest to clear — once the preview pod file is correct, the build will use it.
