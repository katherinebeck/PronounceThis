# RCA — Pronounce This (accent-coach-pro) — ERR_CONNECTION_CLOSED on pronouncethis.us

## Problem statement
A paying customer, redirected to `https://pronouncethis.us/payment/success?session_id=cs_...` after Stripe Checkout (~10:03 local), saw **ERR_CONNECTION_CLOSED** ("unexpectedly closed the connection"). Reporter now sees HTTP 200 on both apex and www, with http→https 301 working — so it looks transient. Asked to check (1) deploy/republish/edge events in ~24h, (2) pod crash loops / OOM / restarts, (3) TLS/cert issue on apex vs www.

Note on precision: the customer's **timezone and date were not provided**, and K8s events older than ~1h are garbage-collected, so I cannot pin the drop to the exact minute. Conclusions below rest on the container termination record (survives GC), deploy history, SSL state and live logs.

## What I verified (evidence)

### Orientation
- Deployment `accent-coach-pro`, template `fastapi_react_mongo_shadcn_base_image`, **frontend_type = cloudflare** (static served from R2 via a Cloudflare worker; `/api` proxied to the k8s backend), tier **tier_0** (mem limit **512Mi**, 2 replicas, HPA off), active run `9737f530-c2ac-4b01-937b-56f68b4cd059`.
- Live now: `GET /` and `/health` → **200** on the default URL; `check_domain_status` → both apex and www **linked** (DNS resolves). App is currently healthy.

### (1) Deploy / republish activity
`describe_deployment_state.recent_runs` shows **5 successful redeploys on 2026-10-09** (UTC): 06:21, 07:23, 20:32, 21:12, and 21:43 (last completed 21:48). Each redeploy ends in a **promote** (atomic traffic flip + reverse-proxy cache invalidation) and tears down the old pods — each flip is a short window where in-flight connections to the origin can be reset. This matches the owner's "republished several times."

### (2) Pod crashes / OOM / restarts — CONFIRMED
- Active pod `...-jqfn4`: `last_termination.reason = **OOMKilled**, exit_code **137**, restarts = **2**`, most recent OOM kill finished **2026-10-10T23:09:26Z**. This is the container being killed for exceeding the **512Mi tier_0 memory limit** (OOMKilled, not a bare exit 137).
- A second replica `...-cqqrk` churned: **Startup probe failed: HTTP probe failed with statuscode 503** (×4), then `Killing`/`SuccessfulDelete` — i.e. a pod that never became ready was torn down.
- Backend logs during restart windows: nginx `connect() failed (111: Connection refused) ... upstream http://127.0.0.1:8001/health` and `upstream timed out` — i.e. the FastAPI backend (uvicorn:8001) was **down/unreachable while restarting**.
- Root driver of the memory pressure / slow start: on **every boot** the app runs a heavy `ingest supervisor: startup ingest (indexed=12697 ...)`. That inflates startup memory (→ OOM at 512Mi) and lengthens startup (→ startup-probe 503 → pod killed → restart → repeat).

### (3) TLS / certificate — apex vs www
- `list_domains`: **pronouncethis.us (apex)** → `verified=true`, `ssl_status=**active**`, provider cloudflare, http validation. **No current TLS fault on the apex** — the domain the customer was on.
- **www.pronouncethis.us** → `verified=false`, `ssl_status=**pending_validation**`. www's cert is not issued, but the customer's screenshot shows the **apex** in the address bar, so www SSL is **not** the cause of her error. It is a separate open item.

## Root cause (most likely)
**ERR_CONNECTION_CLOSED is a transient origin/connection drop, not a persistent cert or app fault.** Two documented conditions on this deployment each produce exactly this kind of brief TLS/TCP reset at the edge→origin, and both were active in the window:
1. **Backend OOMKill + pod restart churn** (CONFIRMED: OOMKilled exit 137, restarts=2; startup-probe 503; nginx 111 connection-refused to the backend). When a replica is OOM-killed / fails its startup probe, the origin refuses/closes connections until a pod is ready again — a few minutes each time.
2. **Promote/traffic-flip during the repeated republishes** (5 redeploys on 2026-10-09; each flip briefly resets in-flight connections and invalidates the edge cache).

I could not isolate which of the two hit her exact request (no timezone/date to map 10:03, and the minute-level K8s events have been GC'd), but both are evidenced and both yield ERR_CONNECTION_CLOSED. The apex TLS certificate was and is `active`, so a cert/TLS failure on the apex is ruled out as the cause.

## Ongoing or resolved?
**The specific outage is resolved** — apex and www both return 200 now and the active pod is `Ready`. **However the underlying cause is NOT fixed and will recur:** the backend is still OOMKilling at the 512Mi tier_0 limit (restarts=2, last kill 2026-10-10T23:09Z) and re-runs the heavy startup ingest on every boot. Until memory headroom and/or the boot-time ingest is addressed, the app will keep dropping connections during each restart — and any payment redirect landing in that window will see the same error.

## Suggested fixes (no changes made)
1. **User — raise the tier (Deployment Panel → Resources).** tier_0 caps memory at 512Mi and the backend is OOMKilled there. A higher tier gives startup headroom and stops the OOM→restart→connection-drop loop.
2. **Code (E1) — fix the boot-time memory/startup cost.** Defer/throttle or run-once the `startup ingest (indexed=12697)` instead of re-indexing on every boot; this is what spikes memory (OOM) and slows startup past the probe window. Also add a real backend `GET /health` route — it currently returns **404** (the probe tolerates 4xx so it still passes, but a proper 200 health endpoint makes readiness/restarts cleaner).
3. **User (domain) — finish www SSL (Deployment Panel → Domains).** `www.pronouncethis.us` is `pending_validation` / unverified; complete its HTTP validation. Not the cause of the apex error, but it leaves www without a valid cert.

## Note for payment safety
Because the drop can land on `/payment/success`, confirm post-payment fulfillment does not depend solely on the browser reaching that page. Logs show `POST /api/payments/webhook → 200`, so if fulfillment is driven by the Stripe webhook the customer's purchase should still be recorded even though her browser showed ERR_CONNECTION_CLOSED — worth the owner verifying for this customer.
