## Root cause (mechanism proven via source + DB; runtime log line not captured)
Source confirms the exact signature the reporter described:
- `backend/supabase_auth.py` resolve_user_email:
  1. `find_one({"supabase_sub": sub})` by the incoming token's sub.
  2. If not found → resolve by email; if the matched doc's `supabase_sub` is non-null AND != incoming sub →
     `logger.warning("login %s resolves to account %s which is linked to another supabase identity", ...)` then `raise IdentityConflict(email)` (lines ~121-129).
- `backend/auth.py` caller_email: `except supabase_auth.IdentityConflict: request.state.auth_error = "inbox_already_linked"` then returns None (lines ~209-211).
- `backend/auth.py` /me: when email is None → returns `AuthMeResponse(authenticated=False, auth_error=...)` with HTTP 200 (lines ~519-525).

katherine's doc is pinned to an OLD Supabase identity (`supabase_sub` 02f1f459…, last_login 2026-09-21). "Continue with Google" yields a Supabase JWT whose `sub` is her Google-provider identity — a DIFFERENT, non-null sub. resolve_user_email therefore finds the email already linked to a different sub → raises IdentityConflict → /api/auth/me returns authenticated:false + auth_error=inbox_already_linked → the frontend signs her out → "Sign in required". This exactly reproduces the symptom.

Why /api/admin/* still returns 200 for her: `caller_email` also honours the legacy admin-issued magic-link JWT cookie, which bypasses the Supabase/resolve path entirely. So her existing cookie session reaches the admin API, but the Google/Supabase login flow does not.

Why regular members are fine: their users doc's supabase_sub matches their current (Google/Supabase) identity, so no conflict.

Inferred (not runtime-observed): that the incoming Google sub differs from the stored 02f1f459 — cannot be confirmed without the live JWT (no app secrets/live Supabase in the sandbox). All other links are proven.

## Remediation
1. Data fix (immediate): clear/repoint `supabase_sub` on katherine's users doc so the next Google login re-links cleanly. Setting `supabase_sub` to null makes resolve_user_email treat it as `(None, sub)` → no conflict → it stamps the new Google sub. (Confirm first that her Google identity's email is exactly katherine@katherinebeck.com.)
2. Code (E1): the identity-linking logic permanently rejects a legitimate user who changed login method (email→Google) — by-design anti-hijack, but it locks out real users. Add a safe re-link policy (e.g., re-link when the new identity's email is verified and matches) and/or surface a clearer UX/admin re-link flow. The IdentityConflict warning should also fire where it can be seen.
3. Supabase (third-party): verify whether katherine has two Supabase identities (original + Google) with different subs; link/consolidate them in the Supabase dashboard so one sub is canonical.
